# Deployment

This deploys the backend + frontend to Render, using [`render.yaml`](render.yaml) (a Render
Blueprint — one file provisions both services), with Postgres and Redis hosted elsewhere on their
own free tiers, since Render's own managed Postgres/Redis aren't free.

No step here costs money on the tiers linked. Render's free web service sleeps after 15 minutes
idle and takes ~30-60s to wake back up on the next request — expected on a free tier, not a bug;
worth mentioning up front if you're sending this link to someone.

## 1. Postgres — [Neon](https://neon.tech)

1. Sign up (GitHub login works, no card needed), create a project.
2. From the connection details panel, copy the host, database name, username, and password
   (Neon shows a full connection string — you can split it, or paste the pieces below).

## 2. Redis — [Upstash](https://upstash.com)

1. Sign up (GitHub login works, no card needed), create a Redis database.
2. Pick a region close to Render's (this deploy uses Render's `frankfurt` region — pick an
   Upstash region in the EU to keep latency down).
3. From the database details page, copy the **endpoint host**, **port**, and **password**. Upstash
   requires TLS, which is why [`render.yaml`](render.yaml) sets `REDIS_SSL_ENABLED=true`.

## 3. Stripe (optional — test mode is fine)

1. [dashboard.stripe.com](https://dashboard.stripe.com) → Developers → API keys (test mode) for
   the secret + publishable keys.
2. Developers → Webhooks → add an endpoint once you know the Render backend URL:
   `https://<your-backend>.onrender.com/api/v1/stripe/webhook`, event types
   `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.canceled` → copy
   the signing secret it gives you.
3. If you'd rather skip Stripe entirely for now, the placeholder values from
   `docker-compose.yml` work — booking creation will 502 at the payment step, same as the local
   Docker smoke test, which is a legitimate documented limitation, not a broken deploy.

## 4. Render — deploy the Blueprint

1. [dashboard.render.com](https://dashboard.render.com), sign up with GitHub.
2. New → Blueprint → pick this repository. Render reads [`render.yaml`](render.yaml) and shows two
   services (`salon-booking-platform-backend`, `salon-booking-platform-frontend`).
3. Fill in the env vars it prompts for (anything marked `sync: false` in `render.yaml`):

   | Variable | Value |
   |---|---|
   | `SPRING_DATASOURCE_URL` | `jdbc:postgresql://<neon-host>/<db>?sslmode=require` |
   | `SPRING_DATASOURCE_USERNAME` | from Neon |
   | `SPRING_DATASOURCE_PASSWORD` | from Neon |
   | `REDIS_HOST` | from Upstash |
   | `REDIS_PASSWORD` | from Upstash |
   | `APP_CORS_ALLOWED_ORIGINS` | your frontend's Render URL, e.g. `https://salon-booking-platform-frontend.onrender.com` |
   | `APP_STRIPE_SECRET_KEY` / `APP_STRIPE_WEBHOOK_SECRET` / `APP_STRIPE_PUBLISHABLE_KEY` | from Stripe, or the `docker-compose.yml` placeholders |
   | `APP_ADMIN_BOOTSTRAP_USERNAME` / `APP_ADMIN_BOOTSTRAP_PASSWORD` | leave blank unless you set `APP_ADMIN_BOOTSTRAP_ENABLED=true` |
   | `VITE_API_URL` (frontend service) | your backend's Render URL + `/api/v1`, e.g. `https://salon-booking-platform-backend.onrender.com/api/v1` |

   `APP_JWT_SECRET` is auto-generated by Render (`generateValue: true` in `render.yaml`) — don't
   reuse the local dev one from `.env`.
4. Deploy. First boot runs all 6 Flyway migrations against the fresh Neon database automatically.
5. Confirm: `curl https://<your-backend>.onrender.com/actuator/health` → `{"status":"UP"}`.

Kafka is intentionally not part of this deploy — see the README's "What's not in the live demo".
The app starts and runs fine without it; the producer/consumer beans just retry a broker that
isn't there, logged as warnings, never blocking a request.

## 5. Wire up CI/CD auto-deploy

[`ci.yml`](.github/workflows/ci.yml) already builds and pushes the backend image to
`ghcr.io/<repo>/backend` on every push to `main`, and pings a deploy hook — it's just not pointed
at anything yet:

1. Render dashboard → the backend service → Settings → Deploy Hook → copy the URL.
2. This repo's GitHub Settings → Secrets and variables → Actions → New repository secret →
   name it `RENDER_DEPLOY_HOOK_URL`, paste the value.
3. Next push to `main`: tests run → image builds and pushes to GHCR → the hook fires → Render
   redeploys.

Note what this hook does and doesn't do: Render Blueprints already auto-deploy on push by
rebuilding [`backend/Dockerfile`](backend/Dockerfile) themselves, so the frontend needs no hook at
all, and the backend would actually redeploy without one too. The hook (and the image
`ci.yml` pushes to `ghcr.io/<repo>/backend`) exists on top of that to make "test → build a
tagged, pullable image → deploy" an explicit, visible pipeline stage rather than something that
happens implicitly inside Render's own build step — useful as a versioned artifact even though
Render's deploy rebuilds from source rather than pulling it.
