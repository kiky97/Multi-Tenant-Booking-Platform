# 可验证的简历表述

项目名建议：**多租户预约与支付平台**。

技术栈：Java 21、Spring Boot 4、Spring Security/JWT、PostgreSQL、Redis、Kafka、React、TypeScript、Stripe、Docker、GitHub Actions。

下面的数字来自真实基础设施上的本地合成测试；它们描述测试范围，不代表生产规模或真实用户业务增长。根据你实际负责并能解释的部分，挑选 2–3 条使用。

## Java 后端 / 分布式方向

- 基于组织成员关系实现 OWNER / ADMIN / STAFF 租户权限控制，在 **20 个租户、60 个成员账号、1,000 条初始服务数据**上建立 **480 次权限矩阵请求**验证，其中 **120 次跨租户 Owner 请求全部返回 403**。
- 修复 Redis 缓存中不可变列表及 record 的 JSON 反序列化异常，使用显式缓存类型、Java 时间支持与版本化 key；在一次本地同一目录 **100 次读取**对比中，将 SQL 语句数从 **100 条降至 1 条（减少 99%）**，该次运行的其余 **99 次暖缓存读取无 SQL**；其他环境的实际数量见评估报告。
- 使用 Redis 原子占位处理相同租户、员工及起止时间的竞争，在 **10 轮 × 32 个 HTTP 调用方、共 320 次尝试**中，每轮仅 **1 次占位成功、31 次返回 409**；另对令牌重放和区间重叠单独建立诊断，明确实现边界。
- 基于 Kafka 的独立消费者组实现确认事件分发，在真实单 Broker 环境验证 **100 条合成事件**分别触发 **100 次通知监听调用和 100 次分析计数更新**；通知侧仅记录日志，未接入真实邮件发送。

精简为三条时，优先保留“租户矩阵”“SQL 减少”“并发占位”，把 Kafka 留作面试展开。

## 全栈方向

- 使用 React/TypeScript 与 Spring Boot 构建组织、服务、员工、预约及支付状态界面，并通过真实 HTTP/JWT/PostgreSQL/Redis 路径验证 **20 租户的 480 次权限请求**，确保所测接口中的角色权限和跨租户访问符合预期。
- 修复服务目录重复读取时的缓存 JSON 异常，补充 **3 项缓存序列化回归测试**；在一次本地 **100 次目录读取**对比中将 SQL 数量从 **100 降至 1**，并保留逐项权限结果及性能采样报告。
- 运行 **46 项后端常规测试**、**21 项前端测试**及 ESLint / 生产构建；使用独立评估作业归档租户权限、HTTP 延迟、缓存查询数、占位竞争及事件分发证据。

当前前端验证是自动化测试与构建，没有声称本次完成了真实支付或全站浏览器端到端测试。

## 数字口径与证据

| 数字 | 可以说明什么 | 不应改写成什么 |
|---|---|---|

| 320 次竞争 / 每轮 1 次成功 | 完全相同起止时间的 Redis 占位创建 | 已杜绝重复预约 / 支付和持久化零超卖 |
| 100 条事件、2 组各观察 100 次 | 单 Broker 健康运行下的双消费者分发 | 发送 100 封邮件 / 消息绝不丢失 / exactly-once |

## 性能数字怎样使用

本次固定 2 个可见处理器、Java 21.0.13、512 MiB 评估 JVM 堆，客户端与服务端共享机器；数据库、Redis 和 Kafka 也在本地。分别使用 1、8、32 个闭环工作线程，各读取 200 次已预热的服务目录。

[实测报告](evaluation/RESULTS.md)列出 P50/P95 和观测请求速率。32 工作线程一组的 **200 次读取均返回 200**；具体 P50/P95 和观测请求速率以报告中的本次结果为准。这些数字可作为面试中的小规模本地实验例子；不能写成生产 SLA、最大吞吐量或“支持 32 个同时在线用户”。缓存的 SQL 数量下降也不代表延迟必然下降；报告保留了直接 DB 与 Redis 路径的实测时间。

## 当前必须解释清楚的并发边界

令牌消费并非原子比较删除：本次 **10/10 轮**并发重放中，都有多个调用返回消费成功（各轮具体次数见报告）。不同起始时间的两个重叠占位也能同时创建。以上是 Redis 服务层诊断，没有测量实际落库的重复预约数量。

因此目前不能使用“防止所有重复预约”“零超卖”“消费令牌幂等”等表述。后续可围绕原子 Lua、区间冲突约束、事务提交前后的占位生命周期继续改进，并以同一评估集及新独立场景复测。

## 面试准备

- 为什么使用成员角色，而不只在用户表存一个全局 role？举同一用户在两个组织有不同权限的例子，解释 JWT 认证与组织授权的分工。
- 为什么缓存修复前，首次读取成功但再次读取失败？解释 JSON 类型信息、不可变列表、record 与显式类型反序列化，说明版本化 key 避免读取旧格式。
- 99% 怎样测出来？解释 Hibernate StatementInspector 按被测线程计数、各自窗口重置、100 次直接读取和 1 冷 + 99 暖的对照；展示原始 JSON。
- 为什么同槽测试通过仍然不能保证不重复预约？解释精确 key 与区间重叠的区别，以及 GET/比较/DEL 的并发窗口和 DB check-then-insert 竞态。
- Kafka 两组都观察到 100 次意味着什么？只证明该次健康链路上的分发；支付事务与事件可靠性、重复消费幂等、邮件送达需要独立设计和实验。
